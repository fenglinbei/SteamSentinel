2026-09-20 已完成环境验收。专用 VM `SteamSentinel-Win11-Lab` 已安装 Windows 11 Enterprise Eval 25H2（build `26200.9457`）、Steam 和官方 VPet（build `25415954`），测试账号已登录，7,842 个正常文件已记录哈希。官方 DemoClock 已验证开发者签名、在线显示和 Private 网络下重新加载。唯一网卡为 `MalwareLab-Private`，无宿主端口或其他 VM；准备期 PowerShell Direct、共享及重定向已封闭并经重启复核。干净检查点 `Clean-Offline-v03-20260920` 的文件/注册表回滚成功，独立导出在新 ID、断网 VM 中成功启动，备份哈希保持不变；两台 VM 均已关机。该导出位于同一 I 盘，不等于另盘灾备。普通用户界面扫描无威胁项，但两个 DLL 的 AMSI 未完成，覆盖保留 `Partial`，见下文和 [环境实施记录](LAB-SETUP-2026-09-20.md)。

2. 创建专用 Windows 11 测试机，并为 Windows 10 支持矩阵保留独立镜像。可从每台 4 vCPU、8 GiB 内存、80–120 GiB 动态 VHDX 起步，按宿主实际资源调整；预留检查点增长和内存转储空间，不能只按当前 VHDX 大小估算。
3. 在没有病毒样本的干净准备阶段安装官方 Steam、VPet、所需运行库和取证工具，准备无资产的专用测试账户；验证合法原版插件能启动，再建立“干净且工具齐全”检查点。避免测试机保存真实 Steam、浏览器、邮箱或开发凭据。
4. 恶意样本阶段使用断网或专用 Private 交换机。需要模拟网络时，仅连接另一台无外网路由的模拟服务 VM；验证无默认外网路由、无到宿主/LAN 的业务通路。Private 交换机只连同宿主 VM，Internal 还连宿主，区别见 [Microsoft Hyper-V 网络说明](https://learn.microsoft.com/en-us/windows-server/virtualization/hyper-v/plan/plan-hyper-v-networking-in-windows-server)。
5. 使用基本会话，关闭剪贴板、磁盘、打印机等重定向及不必要共享。增强会话可重定向宿主资源，见 [Microsoft 会话共享说明](https://learn.microsoft.com/en-us/windows-server/virtualization/hyper-v/enhanced-session-mode)。样本用受控只读介质传入；污染磁盘不直接挂载到宿主浏览，输出优先经独立取证 VM 检查。
6. 每个样本从相同干净检查点创建独立测试分支；保留感染前、感染后、处置后和重启后的文件差异、进程/模块、注册表/任务/服务、网络与工具报告。正常运行、感染观察、清理验证分别留档。
7. 先跑完全离线条件，再用本地模拟端点测试开关。HTTPS、证书校验、请求参数或握手不匹配时，记录模拟未成功，不开放真实攻击服务器作为替代。若需实验性信任配置，只在一次性实验 VM 中记录后回滚。
8. 以测试机时间分别验证门槛前后；调整前控制该 VM 的时间同步，记录时区和实际时钟。不得修改宿主时间。网络响应、日期响应、用户身份解析失败都纳入矩阵。

建议动态矩阵包括：从未运行的样本、已安装未加载、首次通过 VPet 加载、完全离线、模拟 on/off/未来时间、默认日期跨越、SteamID 不可用、游戏占用文件、取消 UAC、清理途中失败、重启后再加载，以及 Steam 重新下载仍订阅的恶意 MOD。每项从可还原检查点开始。

## 查杀升级设计

### 精确规则和有界家族检查

- 在现有规则版本上新增本轮 12 个核心 DLL 的完整 SHA-256，标明外壳、加载器、UI 组件、凭据组件四种角色。三个恶意 ZIP 可加入精确身份，但不能只靠外层包哈希支持重新压缩后的文件。19 个域名经过本轮静态复核，可进入下一规则版本。
- 第一层是精确原件哈希；第二层是 PE 代码节、导出和尾部结构；第三层是外壳到 native 的关系和受限解码后的恶意语义。只有文件名、`.orig.dll`、`native`、`VirtualAlloc` 或高熵现象不确认恶意。
- 在 ArchiveWorker 的现有低权限边界内增加专用 PE 解析器。使用受限长度、64 位范围校验、原件身份绑定和取消令牌；遇到重复/重叠节、越界 RVA、异常尾部长度、过量解码或未知结构时保留缺口。首版只承诺本次已验证封装，不实现任意恶意插件加载或通用代码执行解包。
- 对固定格式进行字节转换，然后复用 `ContentHeuristics` 等已有规则。原始文件哈希、派生哈希、原件内区域、解码器版本和规则来源分别记录。不能把解码副本的 SHA-256 当成原件隔离身份。
- 精确已知恶意项沿用预选策略；新的高置信组合特征先供手动复核。Broker 继续独立验证原始路径与哈希，不信任 UI 文案、低权限 Worker 的单个布尔值或派生样本路径直接授权文件操作。
- 样本原件保留在独立的私有测试资料目录；仓库只收指标和最小化、不可执行的结构/语义 fixture。真实恶意 DLL 不进入安装包、公开源码包或普通证据导出。

### VPet 发现与多文件 Steam 检查

- 保留全 AppID 工坊自动发现，增加 VPet `1920960` 的分类和元数据读取。游戏私有 MOD 目录以官方加载逻辑和新测试机实测确认后适配，不能沿用仅有 `Mods` / `BepInEx/plugins` 的假设。
- 用 `info.lps`、插件目录、同包 `lib/*.orig.dll`、native 成员和可选 `.px_sidecar` 建立同一 MOD 内的关系；所有元数据路径保持本地范围检查，不跟随重解析点、UNC 或目录穿越。
- 支持工坊副本、游戏内副本、手动复制副本和 ZIP 内成员。一个副本命中应提示同一身份的其他本地副本，未检查到的范围明确展示。
- `SteamSecurityScanner` 增加 `index.html`、相关 CSS 及新 JS 模式；`sp.js` 已在旧 `.js` 枚举中，重点补语义。建立 `index.html` 引用、`sp.js` PX 块、chunk 的 `window/self` 路由属性和远程/日期条件之间的有界关系。

- 分别呈现“下载包包含威胁”“本地安装组件命中”“发现运行关联”“Steam 文件被篡改”和“凭据泄漏风险”。不能把压缩包命中直接显示成主机已经感染。

### 系统 AMSI 增强暂停与历史诊断

当前要求以 2026-09-26 用户决定为准：AMSI 是独立增强项，本轮暂停入口和实际调用。基础验收验证没有 AMSI 初始化、扫描、增强额度请求或因未参与而生成的覆盖缺口；即使旧请求中 `UseAmsi=true`，新执行也按关闭处理，并在新报告中记录实际值。正常内容完整读取时可以完成基础扫描，真实读取/解析失败仍不能显示完整。历史报告中的请求值与失败状态不回写、不隐藏。

以下为此前定位过程及证据，不是本轮要求恢复 Norton 的指令，也不是当前 RC 的 AMSI 必过门槛。

2026-09-20 的干净 VM 验收发现：0.2.0 Preview 在 LabUser 普通用户界面扫描官方 DemoClock 时，8 个文件、919,942 B 已完成哈希，未产生威胁项，但两个 DLL 返回“AMSI 不可用”，整次覆盖为 `Partial`。同一普通用户会话的独立无害探针，对文本及这两个原版 DLL 均得到初始化、会话和扫描 `S_OK`，结果为 `AMSI_RESULT_NOT_DETECTED`。Defender 实时保护处于开启状态。

这些证据说明当时 VM 的系统 AMSI 在普通用户环境可用，问题需沿受限 Worker 的调用路径继续定位；尚不能把根因确定为某项令牌权限。0.2.0 的 `AmsiScanner` 初始化失败后只保留空上下文；第 3 步已增加初始化/会话/扫描 HRESULT、架构和完整性级别。第 4 步最终构建仍在宿主复现 Medium/Low 初始化成功、扫描分别返回 `0x80040300`/`0x80070005`；并查明宿主注册的是 Norton AMSI 提供程序，与原 VM 的 Defender 环境不同。这不是原 VM 的根因结论，仍需在一次性干净克隆中对齐条件比较。`ArchiveWorkerClient` 的 Low/Untrusted 门槛保留。

- 已有初始化/会话/扫描阶段、HRESULT、架构与 Worker 完整性级别诊断和中英文资源保留，供历史记录及将来独立增强验收使用。
- 将来恢复该增强项时，再沟通启用范围及普通用户、管理员、受限 Worker、Windows 10/11、可用提供程序的无害输入矩阵。继续保持 Low/Untrusted 边界，不通过提高 Worker 权限完成增强验收。

### ZIP 中文名称与跨语言兼容

0.2.0 对照扫描发现，刮刮乐包最后三个中文文本成员的原始名称为 GBK，且附有有效的 Unicode Path `0x7075` 字段。独立校验器却无条件按 UTF-8 解码，导致它与解压器的条目名称无法对应，留下 3 项、1,421 B 的检查缺口。第 3 步已修复并验证这三个成员均完成完整性及内容检查，第 4 步回归继续通过。已验证的家族配置尾部现已分类；天籁之音另两个依赖的未知尾部继续保留 Partial，不归并为名称问题。

- 让中央目录校验器与解压器采用一致的名称解码策略：尊重 UTF-8 标志；使用前验证 Unicode Path 字段的版本、长度、原始名称 CRC 和严格 UTF-8；明确无该字段的旧编码策略。不得随界面语言切换代码页或静默使用替换字符合并名称。
- 保留原始名称字节、卷/条目位置、CRC 和长度等身份依据。重复字段、名称歧义、规范化冲突、本地头/中央目录冲突仍须明确拒绝或标记缺口；不能删除唯一性校验，也不能仅靠相同 CRC/长度配对条目。
- 校验展示名称和实际读取条目的绑定，再执行目录穿越、绝对路径和重解析点等既有范围校验。用不可执行的合成 ZIP 验证 UTF-8、GBK 加有效 Unicode Path、无扩展字段、错误 CRC、冲突/重复名称及中文/英文系统；同一输入在中英文界面下必须得到同一覆盖结论。

### 清理和恢复流程

建议产品流程：扫描与证据 → 预览精确动作 → 关闭已核验关联宿主 → 隔离恶意加载源和副本 → 处理确认的 Steam 篡改 → 官方恢复 → 原范围及重启复查。

- 复用 `RemediationPlanBuilder`、依赖排序、UAC Broker、文件句柄哈希校验、批次执行和病例复验。不能因 VPet 已签名就排除它加载恶意 DLL 的可能，也不能因此隔离正常 VPet 主程序或其他同名游戏。
- 手工映射及模块卸载可能使普通模块枚举无法看到全部载荷。模块枚举阴性时，不伪造运行关联；在预览中要求用户关闭受影响游戏/Steam，必要时提示重启，完成来源处理后再复查。未知宿主的自动结束进程需独立安全设计，不随新哈希规则开放。
- 按已确认哈希逐文件隔离恶意外壳、加载器与载荷，保留媒体、合法依赖和未判恶意的原插件。若需要禁用整个 MOD，必须有明确归属、范围预览和现有安全能力支撑；不能为了方便启用尚未验收的目录回滚。
- 同时处理已下载/已安装副本，显示订阅与再次下载风险。首次发布先提供精确 MOD/Workshop 身份和退订指引；不根据 depot 包名猜测订阅 ID，不默认改用户所有订阅。
- 先停止感染源，再处理受篡改的 `index.html`、`sp.js`、chunk/CSS 和有恶意关联的禁更配置。采用备份、精确身份验证和官方恢复途径；不对未知 Steam 版本进行大范围正则替换，不把样本的 `_local_patch_backup` 或 `.orig.dll` 自动当可信原件。
- 保留 Steam 游戏库、存档和无关用户设置；Steam 官方补全失败时标记“等待恢复”，不能将“已隔离”当“Steam 已修复”。
- 第 5 步实测暴露安装前置缺口：投放样本前应同时验收程序目录和四个机器状态目录的保护 ACL。实际安装器的权限继承及升级场景需纳入联合验收；已有不可信状态不能通过事后收紧 ACL 自动成为可信数据。
- 复验分别记录动作完成、客户端恢复、原内容范围复扫、系统重启复扫和 VPet 再启动结果。任何未完成项都不能显示成全机安全。提示从可信设备完成账户安全处置，本地工具不索取密码或令牌。

## 英文支持：先分离状态与显示文字

源码盘点发现 App、Core、Broker、Worker、安装器共约 141 个文件含中文，约 2,938 行（含注释，不是独立待翻译字符串数），此外还有规则解释和文档。工作量集中在 Core 结果模型、诊断解释和报告，不能只替换主窗口按钮。

2026-09-21 已完成以下状态基础改造，详见 [状态与原因码设计](STATUS-AND-REASON-CODES.md)。其余页面和流程仍需资源迁移，不能据此宣称完整英文支持：

同日已继续补齐共用结果与诊断的 668 组中英文资源，共计 735 组；Markdown 和记录包说明支持指定语言，JSON 机器值保持稳定。最终资源及受影响回归 356 项通过，见 [资源实施记录](LOCALIZATION-RESOURCES-0.3.0.md)。该记录列明语言设置、完整 UI、后台原有说明、安装器及联合验收的剩余范围。

| 现有位置 | 当前逻辑 | 改造 |
|---|---|---|
| `ScanModels.ExecutionStatus` | 原先通过 CoverageNotes 是否含“取消”判断取消 | 已改为 `ScanExecutionState` 和 `ExecutionReasonCode`，独立保留覆盖状态 |
| `RemediationBatchModels` | 原先用中文状态计数 | 已改为 `RemediationTargetState`；动作执行与验证分开，文字从共享资源生成 |

| Worker 与关联诊断 | 原先解析错误原文或中文检查名称 | 已采用错误原因码、结构化读取状态及稳定 `CheckCode` / 观察 ID |

具体落地：

1. 采用 `MessageId + Arguments`、状态枚举和原因码表达新结果。`RuleId`、动作类型、路径、哈希、时间戳和安全判定保持语言无关。新增报告 schema 版本/兼容读取：旧中文 `Status` 和文本字段仍可显示，缺结构信息的历史记录不得猜成已完成，也不以文案重建处置权限。
2. 建立共享本地化入口及英语默认资源、`zh-Hans` 资源，使用 `.resx` / `ResourceManager` 和 WPF 绑定。该技术路径及自动布局依据 [Microsoft WPF 本地化说明](https://learn.microsoft.com/en-us/dotnet/desktop/wpf/advanced/wpf-globalization-and-localization-overview)；本项目为现代 .NET WPF，不采用仅支持 .NET Framework 的 LocBaml 流程。
3. 已冻结并实现：设置提供 `自动 / 简体中文 / English`。自动跟随当前用户的 Windows UI 语言，中文映射为简体资源，其余使用英语；按用户保存，下次启动生效，当前窗口与任务保持原状。
4. 资源覆盖主窗口、所有页签和弹窗、密码输入/跳过/重试、扫描限制、覆盖缺口、风险解释、处置预览、UAC 前后提示、失败/取消、隔离/回滚、病例、报告、安装/卸载和必要帮助。翻译整句并使用参数，不拼接半句；原始系统错误保留错误码与原文，外层说明本地化。
5. 新管理员窗口继承经白名单校验的语言选择；跨账户仍重新扫描，不跨账户搬运报告或密码。Worker/Broker 优先输出结构化代码，由 UI 本地化；协议、动作授权和报告原始证据不随语言变化。
6. 已冻结并实现：Markdown 和记录包说明默认跟随当前实际界面语言，允许本次另选中/英文；JSON 不新增显示语言字段，同一对象导出保持一致。历史报告原始证据和原中文自由文本保留并说明来源。普通报告脱敏和“不打包样本/密码”要求继续有效。
7. 安装器补全 English / 简体中文选择及自定义消息；沿用原 AppId、安装目录、组件文件名、隔离库路径和升级链。资源卫星 DLL 纳入安装清单、哈希清单、签名与发布核验；不要通过改英文名称制造第二套独立安装。
8. 英文 README、快速使用、结果说明、恢复/回滚说明和 release notes 与功能同步。旧版全部历史设计文档无需追溯翻译，发布必须包含新用户完成核心流程所需的双语文档。

建议固定术语：`已确认恶意 → Confirmed malicious`、`需复核 → Review required`、`部分内容未检查 → Some content was not checked`、`未发现已知威胁 → No known threats found`、`所选动作已完成 → Selected actions completed`。不得将未发现已知威胁译成 Safe/Clean，将严重度译成已确认感染。
