- VPet 按 Steam AppID `1920960` 发现本地 `mod` 和工坊目录，不依赖安装目录名称。既有 `Mods`、`BepInEx/plugins` 范围保留。`info.lps` 只进行至多 64 KiB、256 行的严格 UTF-8 读取，取得名称和声明工坊编号；实际归属仍来自已发现的目录。声明编号不授权退订、隔离目录或结束宿主。
- ZIP 校验器与锁定的 SharpCompress `0.50.4` 解压器使用同一名称策略；保留原始名称字节、本地头与中央目录位置、CRC 和大小。正确绑定后继续执行路径与内容完整性检查。
- AMSI 报告增加稳定诊断码、调用阶段、HRESULT、初始化/会话返回码、进程架构和完整性级别。未提交给 AMSI 的内容记录为 0 字节；调用失败不把原始结果数字误当成成功或威胁判定。诊断经 Worker 协议保留到 JSON，未扩大 Worker 权限。

包命中说明包内有已确认组件，不等于主机正在感染；精确规则接入既有文件处置能力，不代表新感染链的运行关联、Steam 恢复和重启复验已经通过。三个 `.orig.dll` 未仅因封装关系加入恶意规则，也未被指定为可信恢复原件。

## ZIP 名称策略

| 输入 | 处理 |
|---|---|
| UTF-8 标志 | 严格 UTF-8；无效字节拒绝，不使用替换字符 |
| 有效 Unicode Path `0x7075` | 验证版本、长度、原始名称 CRC32、UTF-8；采用声明的 Unicode 名称 |
| 没有 UTF-8 标志或 Unicode Path | 固定 CP437，不随 Windows/UI 语言改变，不猜测本地 ANSI 代码页 |
| 本地头与中央目录 | 原始名称一致；本地 Unicode 字段若存在，必须与最终中央目录名称一致 |
| 重复/冲突 | 重复扩展字段、名称 CRC 错误、未知版本、大小写/分隔符/Unicode NFC 后重名、字段冲突均保留受控缺口 |

依据 [PKWARE APPNOTE 6.3.10](https://pkware.cachefly.net/webdocs/casestudies/APPNOTE.TXT) §4.6.9；规范允许忽略过期或未知版本的 Unicode 扩展，本扫描器选择更保守的缺口策略，以免校验器和解码器给出不同身份。实现接口核对 [SharpCompress 0.50.4 源码](https://github.com/adamhathcock/sharpcompress/tree/0.50.4)，标签解析到 `c083c6efd843a844b0c8f7878787360e815be781`。

## 静态验收

真实样本仅以字节流交给现有 Low Worker 静态扫描，没有加载 DLL、执行载荷、请求样本域名或对样本采取清理动作。新副本留在私有工作目录，没有进入源码发布目录。此前封存的虚拟机、检查点和备份未作改动。

| 用例 | 结果 |
|---|---|
| SmartPet 原包 | 包 + 4 个核心成员命中；14 项，4,667,494 B 展开 |
| 天籁之音原包 | 包 + 4 个核心成员命中；14 项，2,596,337 B 展开 |
| 刮刮乐原包 | 包 + 4 个核心成员命中；75 项，7,469,685 B 展开 |

| 三个新 ZIP，改变外层哈希和成员名称/目录 | 各命中 4 个核心成员，合计 12/12；未依赖原包哈希 |
| 三个随包 `.orig.dll` | 0 个已确认恶意，0 个可处置项；静态范围 Complete |

21 个文件级回归用例全部通过，并核验处置目标仍绑定实际外层路径和哈希。刮刮乐中的 `介绍.txt`（1,332 B）、`名字.txt`（18 B）、`标签.txt`（71 B）均有独立 SHA-256，完整性、内容检查及最终状态均为 Complete；较 0.2.0 补齐 3 项、1,421 B。

三个恶意原包的整体状态仍为 **Partial**：现有解析器尚未解释部分 PE 尾部范围。这些缺口继续呈现为 `CONTAINER-UNKNOWN-RANGE`，已知恶意身份仍然成立；第 4 步负责增强该家族解码，不能通过删除缺口完成验收。天籁之音的两个其他依赖也保留未知尾部说明。

最终构建为零警告、零错误；全量自测 **1,807 通过、0 失败、0 跳过**，专项及关联回归 **128 通过、0 失败、0 跳过**。专项覆盖 UTF-8、GBK+Unicode Path、CP437、中文/英文区域设置一致性、CRC 与路径穿越、冲突名称、VPet 发现边界及 AMSI 错误阶段，还复核成员取消/预算耗尽后的身份保留与版本一致性。区域设置测试不代表英文界面已经实现。

## AMSI 固定复现

使用 `--v030-amsi` 明确选择官方 DemoClock 夹具。入口先校验两个 DLL 的固定哈希及目录总量，随后分别进行直接 API 调用和产品 Low Worker 扫描；不运行插件。

| 环境 | 初始化 / 会话 | 扫描阶段 | 解释 |
|---|---|---|---|
| 此前干净 VM，LabUser 独立探针 | S_OK / S_OK | 三个无害输入均 S_OK，结果 1 | 属于第 2 步原始证据 |
| 此前干净 VM，0.2.0 GUI/Worker | 未保留 HRESULT | 两个 DLL“AMSI 不可用” | 不足以确定失败阶段 |
| 本轮宿主机，x64 Medium 直接 API | S_OK / S_OK | 三次 `0x80040300` | 真实扫描调用失败；未解释其提供程序内部含义 |
| 本轮宿主机，x64 Low Worker | S_OK / S_OK | 两个 DLL 均 `0x80070005` | ScanBuffer 访问被拒绝；诊断明确保留 Low |

宿主机复现说明新诊断链有效，不等于此前 VM 根因已解决；两台机器不能合并成同一环境对照。仍需在干净测试克隆中执行同一新探针，并扩大普通用户、管理员、Windows 10/11 和提供程序矩阵。不得通过提升 Worker 权限或关闭 AMSI 消除覆盖提示。AMSI 会话为空时允许继续扫描的行为依据 [Microsoft AmsiScanBuffer](https://learn.microsoft.com/en-us/windows/win32/api/amsi/nf-amsi-amsiscanbuffer)，会话失败码仍保留。
